A blueprint closes one recurring RevOps gap with one custom object, a shared core of fields, and two to five record types, one for each variation of the motion. The blueprint document names every field, writes every validation rule and formula out in full, lays out each page and report, and sequences the build into phases that get built and tested one layer at a time.

What a Blueprint Is

Most RevOps pain lives in the gaps between standard objects. Meeting notes pile up in Activities, deal help is requested over Slack, ownership changes happen without an audit trail, and go-lives slip in a spreadsheet. Each of those is a motion that repeats every week, and each deserves a structured home that leadership can report on.

A blueprint is written for two readers at once: a VP should be able to read the scope section and tell me what to cut, and an admin should be able to build from it without asking me a question.

Format. A two-page executive summary for leadership, and a 15 to 25 page build plan that ends in a punchlist in build order.

Anatomy of a Blueprint Object

Shared coreevery record type
Parent Account, optional Opportunity, owner, status, health or priority, key dates and a resolution. These fields live once and report once, so “everything happening on Acme this quarter” is a single related list.
Record typestwo to five per object
Each adds its own fields, page layout, picklist values and validation profile. A QBR asks for MEDDICC gaps; a Key Interaction never sees them. Users get a short, specific form while the org keeps one tab and one sharing model.
Calculated layerbuilt last
Formula fields, roll-ups, list views, reports and a dashboard. They go in after the hand-entered flow is proven, because if the manual data flow does not work, calculated fields only hide it.

Why record types instead of more objects

One report type covers every variation, so managers compare them side by side. One sharing model, one permission set and one tab to maintain, however many variations the business adds.

A place for the next idea

A new need becomes a new record type on an existing object before anyone proposes another object. Most rules fire only when a record is marked done, so users can still save a draft mid-meeting.

The Five Stages

StageWhat Happens
1 · Frame Start from what exists: a requirements doc, an overgrown spreadsheet, or the report a leader can never get. I work backward from that report.
2 · Place Decide where the idea lives before deciding how to build it. Usually that is a record type on one of the four objects (see the placement test below).
3 · Scope Write down what is in, deferred and dropped, by name and with the reason. My open questions are flagged in the document rather than resolved quietly.
4 · Specify Field by field: API name, type, picklist values, help text. Validation rules with their conditions and exact error messages. Formulas written out. A layout per record type, plus related lists and reports.
5 · Sequence Data model, then layouts, then validation rules, then formulas and reports, with sandbox UAT between phases. Automation follows once the manual flow works.

The Test That Settles Scope

Most “can we also track…?” debates end once the idea is placed. Each answer is a larger commitment than the one above it, and only the last adds a new object to the org.

If the idea is…It becomesExample
One-to-one with a record Fields on the object that already exists. A close plan or competitor captured on the Opportunity.
A variation of a motion A new record type on an existing blueprint object. Win/Loss Review added to Customer Interaction.
A new recurring motion A new blueprint object, launched with its first record types. Rev Ops Request, launched with three record types.
