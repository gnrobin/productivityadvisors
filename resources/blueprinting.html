A blueprint is the document that creates a roadmap between problem definition and a plan toward a solution. It names the objects, record types and fields, writes every validation rule and formula out in full, lays out each page, list view and report, and sequences all of it into phases that get built and tested one layer at a time.

What a Blueprint Is

It is written for two readers at once: a VP should be able to read the scope section and tell me what to cut, and an admin should be able to build from it without asking me a question.

Format. Typically 15 to 25 pages, ending in a punchlist in build order.

The Five Stages

StageWhat Happens
1 · Frame Start from what exists — a requirements doc, an overgrown spreadsheet, or the report a leader can never get. I work backward from that report.
2 · Shape Decide what the idea is before deciding how to build it: fields on something that exists, functionality added to it, or a new child object (see the tier test below).
3 · Scope Write down what is in, deferred and dropped — by name, with the reason. My open questions are flagged in the document rather than resolved quietly.
4 · Specify Field by field: API name, type, picklist values, help text. Validation rules with their conditions and exact error messages. Formulas written out. Layouts per record type, plus related lists and reports.
5 · Sequence Data model, then layouts, then validation rules, then formula fields — with sandbox UAT between phases. Formulas go last on purpose: if the manual data flow does not work, calculated fields only hide it.

Example Blueprinting Scenarios

  • Replacing activity sprawl. Meeting notes, site visits and calls buried in unreportable Activities, moved onto one object a manager can report on.
  • Encoding a post-sales methodology. The QBR and annual planning cycle as structured records — MEDDICC gaps, champion testing and forecast confidence on the review; goals, KPI targets and attainment on the plan.
  • Project and lifecycle tracking. Customer and partner onboarding on one project object with phases, health and go-live slippage.
  • Escalations and save plays. Escalations with severity, owner and resolution; at-risk plays as trigger, action taken and outcome.
  • Delivery, compliance and channel artifacts. Recurring data loads, covered populations, agreements with version and expiry, partner payouts and co-marketing.

The Test That Settles Scope

Most “can we also track…?” debates end once the idea is placed in a tier. Each tier is a larger commitment than the one above it, and only the third adds a new object to the org.

TierWhat Gets BuiltExample
Attribute Fields added to a standard or custom object that already exists. A close plan or discount approval captured on the Opportunity.
Add-on Record types, layouts, validation rules and automation on an existing object. An executive business review beside the rep-level QBR.
Standalone A new child object for records that recur over time against a parent. Eligibility-file loads logged per account, one record per load.
