Building the RevOps Loop

AI agents will speed up whatever operating model you already have. The RevOps Loop builds one they can strengthen: governance gives you numbers people trust, the context layer makes them useful, systems get them to the right people at the right moment, and rhythm turns them into decisions. A quarterly retro sends what broke back to the start.

The RevOps Loop framework comes from Lonny Sternberg, VP RevOps at Veriforce, as he walked through it with Janis on the Weflow podcast. The build steps, deliverables and Salesforce guidance are from Productivity Advisors.

Why Build the Loop

AI agents will soon pull pipeline, calculate forecasts and brief reps on their own. If your definitions are loose, your data is split across tools, and your weekly meetings run on side spreadsheets, agents will make those problems bigger and faster.

This blueprint is a build guide for each part of the loop. Every stage uses the same template: its purpose, the design questions to answer, the build steps in order, the deliverables, how to build it in Salesforce, who owns it, and the signs that it is breaking.

How the Loop Works

Each stage produces what the next one depends on. Build them in order the first time, then run the quarterly retro to keep the loop closed.

1

Governance

Purpose: create one shared language for the whole GTM org, people and agents alike, so every number means the same thing wherever it shows up.

Design questions

  • Which 10–15 metrics run the business, and what is the exact formula for each?
  • What data has to be captured, at which stage, for those formulas to work?
  • Who is accountable for each metric and for the fields behind it?
  • Where is the one place leadership looks for the official number?
  • Which department owns each definition, and who settles disputes?

Build steps

  1. Pick the core metrics. Start with the ones in the forecast and board deck: pipeline created, pipeline coverage, bookings, ARR, win rate, cycle time, net retention.
  2. Write the formulas. For each one, record the formula, the inclusions and exclusions (for example, whether renewals count as pipeline), the source fields and how often it refreshes.
  3. Define data capture by stage. For each opportunity stage, list the fields that must be filled before a deal can move forward. Do the same for leads, accounts and renewals.
  4. Assign owners. Each metric gets a business owner who signs off on the definition and a data owner who answers for accuracy. Marketing owns pipeline sourcing, Sales owns stage criteria, CS owns retention, Finance owns bookings and ARR.
  5. Centralize the official number. Name one certified report or dashboard per metric as the source of truth, and retire the competing versions.
  6. Make it apply to agents too. Any agent that reports or calculates a metric must use the certified definition and source, not its own query.
  7. Set a change process. Definition changes get versioned, approved by the owner and announced before they take effect.

Deliverables

DeliverableWhat it contains
Metric dictionaryName, formula, inclusions and exclusions, source fields, refresh cadence, business owner, data owner
Stage-exit criteriaRequired fields and evidence for each opportunity stage
Ownership matrixDepartment and named owner for every metric and key field
Certified report listThe one official report or dashboard for each metric
Change logDated record of definition changes and who approved them

In Salesforce

  • Validation rules and required fields enforce stage-exit criteria at the point of entry.
  • Path with guidance for success shows reps what each stage requires.
  • Field descriptions and help text carry the dictionary definition into the record page.
  • A certified dashboards folder with restricted edit access holds the official numbers.
  • Formula fields calculate shared metrics once in the org rather than in each report.

Signs it's breaking

  • Two leaders bring different numbers for the same metric.
  • Reps fill required fields with placeholder values.
  • An agent's answer doesn't match the dashboard.

Owner and cadence: RevOps runs it, and each department head signs off on their own definitions. Review the dictionary every quarter, and approve changes as they come up.

The Context Layer

Purpose: give people and AI the right information at the right time. Lonny describes a good context layer as three parts working together: governance, which makes it usable; first- and third-party data combined into a knowledge layer; and clean, unified data in the CRM.

Design questions

  • Is the CRM data clean enough to trust: few duplicates, few stale records, required fields filled in?
  • Is engagement (emails, meetings, calls) captured automatically, or only when reps remember to log it?
  • Which first-party data (product usage, billing, support) should sit next to each account and deal?
  • Which third-party data (enrichment, intent, firmographics) do you actually use, and which source wins when they conflict?
  • Can an agent read your definitions, or do they live only in people's heads?

Build steps

  1. Clean the core. Dedupe accounts and contacts, merge records, archive dead ones, and retire fields with low fill rates or no owner.
  2. Automate activity capture. Sync email, calendar and call data to the right records automatically, so the CRM reflects real engagement rather than rep diligence. This is the layer Weflow customers focus on.
  3. Join first-party data. Bring product usage, billing status and open support cases onto the Account, keyed on a reliable shared ID.
  4. Choose third-party sources. Pick one source of truth per data type, such as firmographics or intent, set rules for which one wins, and cut overlapping vendors.
  5. Publish definitions in a form machines can read. Put the metric dictionary from Stage 1 somewhere agents can query, such as a semantic layer, a documented data model, or an MCP server that exposes certified definitions.
  6. Measure freshness. Track how old the data is when someone or something uses it, and set a target for each source.

Deliverables

DeliverableWhat it contains
Data quality baselineDuplicate rate, fill rates on key fields, stale-record count, measured before and after cleanup
Activity capture mapWhich engagement data flows to which objects, and from which tools
Account 360 data modelFirst- and third-party fields joined to Account and Opportunity, with the source for each
Source-of-truth rulesWhich system wins for each data type
Machine-readable dictionaryStage 1 definitions exposed where agents can use them

In Salesforce

  • Duplicate and matching rules prevent new duplicates; a one-time merge clears the existing ones.
  • Einstein Activity Capture or a dedicated capture tool logs email and calendar activity.
  • Data Cloud, a warehouse sync, or a lighter connector brings product and billing data onto the Account.
  • The Salesforce MCP server or Agentforce data access gives agents governed access to records and definitions.
  • Field usage reports (fill rate by field) find fields to retire.

Signs it's breaking

  • Reps keep their own account notes outside the CRM.
  • An agent answers confidently from a stale or duplicate record.
  • Product usage comes up in renewals but isn't on the account.

Owner and cadence: RevOps and systems admins own it, with data engineering if you have a warehouse. Run data-quality checks monthly and refresh the baseline quarterly.

Systems

Purpose: design the processes that let each person get their own context when they need it, without waiting on RevOps to pull a report.

Design questions

Lonny designs systems around four questions. Answer them for each role:

  1. How does someone get the information? A dashboard, an alert, an agent's answer, or a person.
  2. Who needs it, and at what moment? A rep before a call, a manager before a deal review, a CSM 120 days before renewal.
  3. Where will they look for it? The record page, Slack, their inbox, or the meeting itself.
  4. How do they share information back so the collective picture improves? Updating a field, a call note an agent captures, flagging a correction.

Build steps

  1. List roles and their recurring questions. For each role (SDR, AE, manager, CSM, leader), write down the five questions they ask most often and where they get the answer today.
  2. Map questions to moments. Place each question on the deal or customer timeline: prospecting, discovery, deal review, close, onboarding, renewal.
  3. Choose a delivery channel for each moment. Put the answer where the person already is. Prefer push (an alert or a brief) over pull (go find the report) for anything time-sensitive.
  4. Build the delivery. Record-page components, Slack alerts, scheduled briefs, agent prompts. Keep each one tied to a certified source from Stage 1.
  5. Design write-back paths. Make it a single step to correct a field, add context or flag an error, so what people know flows back into the context layer.
  6. Retire what nobody uses. Cut reports and dashboards with no regular viewers. Every one you keep is something to maintain.
  7. Measure adoption by role. Treat low use as a design problem, not a training problem.

Deliverables

DeliverableWhat it contains
Role × moment mapEach role's key questions, the moment they arise, and where the answer is delivered
Delivery inventoryEvery dashboard, alert, brief and agent, with its owner, audience and source
Write-back pathsHow each role corrects or adds to the shared picture
Adoption reportUse by role and by asset, reviewed quarterly

In Salesforce

  • Dynamic Forms and Lightning record pages surface the right fields and components for each role and stage.
  • Slack integration and Flow push alerts for stage changes, risk signals and renewal windows.
  • Agentforce or MCP-connected agents answer role-specific questions from governed data and draft pre-call or deal briefs.
  • Quick actions and screen flows make write-back a one-click update.
  • Report and dashboard usage data shows what to retire.

Signs it's breaking

  • People still ask RevOps for numbers they could get themselves.
  • Alerts get muted because there are too many or they aren't relevant.
  • Corrections happen in Slack threads and never reach the record.
  • Dashboards keep multiplying while use stays flat.

Owner and cadence: RevOps designs it with each team's manager. Review the role × moment map at every planning cycle and whenever a role or process changes.

4

Rhythm

Purpose: use what the context shows to decide where to spend time each week, and catch problems early enough to still do something about them. Rhythm covers deal reviews, forecast calls, board meetings and annual planning.

Design questions

  • Which meetings make up the operating cadence, and what decision does each one exist to make?
  • Which signals should change how leaders spend their week?
  • At what level does each signal trigger action?
  • Do board reporting and annual planning use the same metrics as the weekly meetings?

Build steps

  1. Define the cadence and the decision behind each meeting. A weekly pipeline review decides where to add pipeline effort, a weekly forecast call commits a number and names the risks, a monthly business review adjusts resources, and the quarterly board meeting and annual plan set targets.
  2. Pick three to five leading signals with thresholds. For example: pipeline coverage below 3× for next quarter, more than 40% of the quarter riding on five deals, deals slipping two stages without activity, or a drop in usage on renewal accounts. Set your own thresholds from history.
  3. Write the playbook for each signal. Pipeline is short, so shift SDR and marketing effort there. A few big deals will decide the quarter, so get executives in front of those buyers, on a plane if needed. A renewal looks at risk, so start the save plan now.
  4. Run meetings from live context. Run the deal review and forecast call from CRM views and dashboards, not from side spreadsheets prepared the night before.
  5. Send a weekly signal brief. A short written summary, before the week starts, of which signals crossed their thresholds and what is being done about each.
  6. Tie the top of the house to the same numbers. Board metrics and annual plan inputs come from the same certified definitions as the weekly meetings.

Deliverables

DeliverableWhat it contains
Operating calendarEach meeting, its decision, attendees, inputs and owner
Signal definitionsEach leading signal, its threshold and its source
Signal playbookThe action each signal triggers, and who owns it
Weekly signal briefThe template, plus who drafts it and who reviews it
Board metric bridgeHow each board metric maps to the operating dashboards

In Salesforce

  • Collaborative Forecasts and pipeline inspection run the forecast call from live data.
  • Opportunity history and field history power slippage and stage-change signals.
  • Dashboard subscriptions and Slack digests deliver the signal view before each meeting.
  • An agent can draft the weekly signal brief from certified reports; a person reviews it and owns the decisions.
  • Board and plan dashboards sit in the certified folder and use the same formula fields.

Signs it's breaking

  • The forecast call spends its time arguing about numbers instead of deciding.
  • Problems come up in week 10 of a 13-week quarter.
  • Board numbers are rebuilt by hand every quarter.
  • Leaders' calendars look the same whatever the signals say.

Owner and cadence: the CRO or GTM leader owns the rhythm, and RevOps runs the machinery behind it. Signals are watched weekly, and thresholds are reviewed quarterly.

Closing the Loop: The Quarterly Loop Retro

Purpose: each quarter, check every part of the loop, find what is breaking it, and fix one thing in each stage. This is what makes it a loop and not a one-time project.

Who and when. The RevOps lead runs it. The CRO or GTM leader, the heads of Marketing, Sales and CS, a Finance partner and the systems admin attend. Allow 90 minutes, in the first two weeks of the quarter.

Agenda

  1. What the quarter taught us (15 min). Which calls were right, which surprised us, and how early each problem was visible.
  2. Governance check (15 min). Definition disputes, changes requested, fields gone stale, agent answers that didn't match the dashboard.
  3. Context check (15 min). The data-quality baseline compared with last quarter, freshness against target, gaps people worked around.
  4. Systems check (15 min). Adoption by role, alerts that were muted, questions still sent to RevOps by hand.
  5. Rhythm check (15 min). Signals that fired and what was done, signals that should have fired and didn't, thresholds to adjust.
  6. Pick the fixes (15 min). One fix per stage, each with an owner and a due date. Fix the weakest stage first: a strong rhythm can't make up for numbers nobody trusts.

How fixes feed back

What the retro findsWhere the fix goes
A metric was disputedStage 1: update the dictionary
People worked around bad dataStage 2: fix the source or join
Answers weren't there when neededStage 3: update the role × moment map
A problem surfaced too lateStage 4: add or retune a signal

Output: a one-page retro note covering what the quarter taught you, the four fixes with owners and dates, and any definition changes to announce. Last quarter's fixes are the first item on the next retro's agenda.

Rollout: Standing Up the Loop in 90 Days

Build in stage order and don't skip the gates. Each phase makes the next one worth doing, and the loop closes with the first retro at day 90.

The gates matter most for AI. Only put an agent on a GTM metric once its definition has been signed off and its data comes from a certified source.
